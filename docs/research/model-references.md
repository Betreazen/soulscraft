# Референсы моделей, телеграфы атак, оружие в руке и броня

Дата: 2026-11-11. Исследование для SoulsCraft: souls-like мобы в ванильном стиле (кубоиды, 16 px на блок, без HD). Модели и анимации делаем в Blender, превью рисуем в three.js.

Пометки:
- **[исх.]**: проверено по декомпилированному коду клиента (Mojang mappings) или по исходникам мода.
- **[вики]**: взято с minecraft.wiki или другой вики.
- **[не проверено]**: по памяти или из вторичного источника, первоисточник не открывал.

Использованные декомпиляции (это не официальные выкладки Mojang; их стоит читать, но не копировать в репозиторий):
- 1.20.1: [Blackjack200/minecraft_client_1_20_1](https://github.com/Blackjack200/minecraft_client_1_20_1)
- 1.21.11: [rrrRex1024/minecraft-1-21-11-source](https://github.com/rrrRex1024/minecraft-1-21-11-source) (видел только фрагменты через поиск по коду)
- 26.2: [Renekovski/26.2-mcp](https://github.com/Renekovski/26.2-mcp)

Ключевые числа держания предмета в руке **совпадают в 1.20.1 и 26.2**. Значит, они стабильны как минимум с 1.20.

## 1. Референсные модели

### 1.1. Ванильные мобы: главная планка стиля

| Моб (версия, год) | Чем хорош | Что взять для SoulsCraft |
|---|---|---|
| **Warden** (Java 1.19, 2022) [вики] | Огромный силуэт из простых кубоидов. Голова без глаз, «рога»-сенсоры. Атаки предупреждают свет и звук: бирюзовые частицы из груди и звук зарядки перед звуковым ударом. Подсвеченные «души» в груди и пульсация (отдельные emissive-слои текстуры). | Телеграф делается не только позой. Свечение части модели, частицы из конкретного места и отдельный звук «зарядки» работают как гарантированный сигнал. Emissive-слой подходит для «слабых мест». |
| **Ravager** (1.14, 2019) [вики] | Широкий низкий силуэт, голова на длинной шее как молот. Есть понятное окно наказания: если укус заблокирован щитом, с шансом 50% ravager оглушён 40 тиков, потом рычит с отбрасыванием. | Готовый souls-паттерн «блок щитом → стан → контратака врага». | **Evoker / Vindicator / Illusioner** (1.11, 2016; illusioner 1.12, 2017) | Гуманоид 64×64 со скрещёнными руками (отдельный кубоид `arms`). Vindicator держит топор через `ItemInHandLayer`. | Цвет частиц говорит, какое заклинание идёт: фиолетово-серый для клыков, фиолетово-белый для вексов. | **Breeze** (1.21, 2024) [вики] | Модель почти без тела: голова, стержни и вихрь-«юбка» из отдельных полупрозрачных слоёв. Перед прыжком сжимается «как пружина». Перед выстрелом звучит отдельный звук `inhale`, перед прыжком `charge`. Кулдаун заряда ветра 32 тика (Java). | Образец летающего или парящего врага: силуэт держат вращающиеся элементы, а телеграф даёт сжатие плюс звук. |
| **Creaking** (1.21.4, 2024) | Высокий худой силуэт с непропорционально длинными конечностями. Двигается, только когда на него не смотрят. | **Bogged** (1.21, 2024) | Скелет с грибами и мхом: оверлей-слой поверх ванильного скелета. | Варианты одного моба делаются оверлеем, без новой геометрии. |
| **Iron golem** (1.2, 2012) | Классический тяжёлый удар: обе руки вверх, `attackAnimationTick = 10` [исх.]. | Минимально читаемая «тяжёлая атака» за 10 тиков. Это нижняя граница: у нас замахи дольше. |

### 1.2. Летающие и водные (ваниль)

- **Phantom** (1.13, 2018): плоское тело и крылья из двух сегментов. Перед пикированием описывает круги. Силуэт читается снизу на фоне неба, это и есть главный приём для летунов.
- **Ghast** (1.0) и **happy ghast** (1.21.6, 2025): куб с щупальцами-полосками. Перед выстрелом открывает глаза и рот (отдельная текстура «стрельбы»). Самый дешёвый телеграф: сменить текстуру лица.
- **Vex** (1.11): маленький гуманоид с мечом. Во время атаки текстура краснеет (charging) [не проверено].
- **Guardian / Elder guardian** (1.8, 2014): одна крупная деталь (глаз) плюс шипы, которые выдвигаются и втягиваются. Лазер заряжается несколько секунд, луч меняет цвет [вики, без чисел]. Это эталон «долгого телеграфа» для водного врага.
- **Drowned** (1.13): гуманоид с полупрозрачным оверлеем, держит трезубец. Перед броском поза «рука назад».
- **Axolotl** (1.17, 2021): маленькая модель, жабры из плоских плоскостей (0-толщина). Показывает, что «детальная, но ванильная» геометрия допустима.

### 1.3. Слаймы

- **Slime**: внутренний непрозрачный куб (глаза, рот) и внешний полупрозрачный куб. Сжатие и растяжение при прыжке. Это самый честный телеграф: приземление предсказуемо.
- **Magma cube**: 8 горизонтальных слоёв, которые при прыжке расходятся «гармошкой». Расхождение слоёв видно издалека, это уже телеграф.
- **Модовые слаймы**: слаймы Tinkers' Construct (sky / ender / ichor) [не проверено], Conjured Slime и Corrupted Cauldron из Minecraft Dungeons [не проверено], Caramel Cube из Alex's Caves (Alexthe666, 2023) [не проверено].
- **Вывод для наших вариантов слаймов**: сохранить двухслойность «ядро + желе». Новое (шипы, вложенное оружие, расслоение) добавлять внутрь ядра или на оверлей. Телеграф делать через squash-and-stretch с заметной паузой «сжат».

### 1.5. Оружие и броня в ванильном стиле

- **Ваниль** [исх., JSON из 26.2]:
  - Меч / топор (`item/handheld`): `thirdperson_righthand` rotation `[0,-90,55]`, translation `[0,4,0.5]`, scale `[0.85,0.85,0.85]`. Для левой руки rotation `[0,90,-55]`.
  - Обычный предмет (`item/generated`): `thirdperson_righthand` rotation `[0,0,0]`, translation `[0,3,1]`, scale `0.55`.
  - **Булава (mace, 1.21, 2024)** (`item/handheld_mace`): как handheld, но translation `[0,4,1]`, scale `1`.
  - **Копьё (spear, 1.21.11, дек. 2025)** (`item/spear_in_hand`): rotation `[5,270,-40]`, translation `[0,2,2]`, scale `[1.7,1.7,0.85]`. Это пример длинного древкового оружия на базе плоского спрайта, растянутого в 1.7 раза. Атака-укол: `SwingAnimationType.STAB` и `SpearAnimations` [исх.].
  - **Трезубец**: модель «special» (`minecraft:trident`, отдельная entity-модель). `trident_in_hand`: rotation `[0,60,0]`, translation `[11,17,-2]`. Это пример 3D-оружия с собственной моделью, а не спрайта.
- **Better Combat** (ZsoltMolnarrr, 2022) [GitHub](https://github.com/ZsoltMolnarrr/BetterCombat): ожидает, что все предметы держатся «как меч», и поворачивает их в анимациях. Для поправки положения в покое есть позы под конкретное оружие (README). Анимации делаются **в Blender** по их шаблону `animation_template.blend` (см. §2).
- **Epic Fight** (Yesman, сейчас Antikythera Studios) [GitHub](https://github.com/Antikythera-Studios/epicfight): свой скелет (armature) с суставом-сокетом `toolR` для оружия [исх.]. Это прямой аналог нашего «hand socket».
- **Наборы брони**: MC Dungeons Armors / Dungeons Gear (порты сетов из Dungeons) [не проверено]; Epic Knights (Magistu): ванильная плотность пикселей и объёмные детали (гребни, наплечники) [не проверено]. Общий приём: дополнительные кубоиды поверх стандартного армор-меша, текстура при этом остаётся в пиксельной сетке 64×32.

## 2. Телеграфы атак в стиле Minecraft

### 2.1. Схема и опубликованные числа

Классическая схема: anticipation → action → recovery. В модах она закреплена явно:

**Better Combat** ([animations/README.md](https://github.com/ZsoltMolnarrr/BetterCombat/blob/main/animations/README.md)) [исх.]:
- Рекомендуемая длина атаки 20 тиков, для одноручного и двуручного оружия.
- Фазы:
  - **Upswing**: 0–50%, easing in-out, один ключ на 50% («ready to strike»).
  - **Tipping point**: 50–60%, ease-in, ключ на 60%.
  - **Hit end**: 60–70%, ease-out.
  - **Downwind**: 70–100%, ease in-out.
- Поле `upswing` в атаке должно совпадать с tipping point. Анимация масштабируется под кулдаун оружия.
- Удар можно отменить во время upswing (feint).

**Epic Fight**, `AttackAnimation.Phase(start, antic, preDelay, contact, recovery, end, …)` [исх.]. Примеры из `Animations.java` (секунды; `ComboAttackAnimation(transition, antic, contact, recovery)`):

| Атака | antic | contact | recovery |
|---|---|---|---|
| sword_auto1 | 0.0 | 0.1 | 0.4 |
| longsword_auto1 | 0.25 | 0.35 | 0.5 |
| tachi_auto1 | 0.35 | 0.4 | 0.55 |
| spear_onehand_auto | 0.35 | 0.45 | 0.75 |
| greatsword_auto1 | 0.15 | 0.25 | 0.65 |
| axe_auto1 | 0.05 | 0.15 | 0.7 |

Это атаки игрока, у мобов замах нужно делать заметно длиннее.

### 2.2. Выводы для наших мобов

Это рекомендации, а не опубликованные нормы:
- Ванильные «тяжёлые» удары укладываются в 10–15 тиков, но читаются за счёт звука и частиц. Souls-замах у нас должен быть **дольше Epic Fight greatsword (0.15 с)**. Разумный старт: 12–24 тика anticipation на тяжёлый удар. Число проверить плейтестом.
- Delayed attack (задержка на вершине замаха) делается удержанием позы плюс отдельным звуком на старте замаха. Тогда игрок, который реагирует на звук, наказан, а игрок, который смотрит на модель, нет.
- Каждой атаке нужен **уникальный сигнал**: поза, звук и, при необходимости, частицы из конкретной кости. Пример: warden выпускает частицы из груди, evoker красит частицы по типу заклинания.
- Recovery: явная поза «застрял» плюс окно уязвимости, как у Wroughtnaut и стана ravager.

### 2.3. Инструменты анимации

- **GeckoLib** ([wiki](https://wiki.geckolib.com/), GeckoLib 5 покрывает MC 1.21.5–26.3): Bedrock-формат анимаций (`.animation.json`), контроллеры анимаций на стороне Java, keyframe-триггеры для звуков и частиц. Звук замаха и частицы привязываются к кадру, а не к тику AI [не проверено в деталях API 5.x].
- **Bedrock animation controllers** ([bedrock.dev](https://wiki.bedrock.dev/animation-controllers/animation-controllers-intro)): машина состояний. Переход между состояниями не чаще одного раза за тик, переходы проверяются сверху вниз. При перезагрузке сущности контроллер сбрасывается, поэтому начальное состояние должно перезапускать критичные анимации.
- **Emotecraft / PlayerAnimator** (KosmX, с 2020) [GitHub](https://github.com/KosmX/emotes): ими пользуется Better Combat. Анимации игрока экспортируются из Blender скриптом.
- **Epic Fight**: свой формат анимаций и скелета. Его фазы antic/contact/recovery стоит принять как словарь в нашей спеке мувсетов.

## 3. Предмет в руке в Java: точная математика

### 3.1. Цепочка трансформаций

Порядок операций `PoseStack`, от мира к вершине предмета. Проверено в 1.20.1 и 26.2 [исх.].

1. **`LivingEntityRenderer.render`**:
   - `setupRotations`: `rotY(180° − bodyYaw)`;
   - `scale(-1, -1, 1)`;
   - масштаб моба (`scale(...)`);
   - `translate(0, -1.501, 0)`.

   В итоге пространство модели получается такое: **+Y вниз**, начало на 24 px (1.5 блока) над ногами. Значение 1.501, а не 1.5, предотвращает z-fighting с землёй. Моб смотрит в **−Z модели**, **+X модели = левая сторона моба** (левая рука при X=+5).
2. **`HumanoidModel.translateToHand(state, arm, pose)`**: в 26.2 сначала `root.translateAndRotate`, затем `getArm(arm).translateAndRotate`. В 1.20.1 только рука.
3. **`ModelPart.translateAndRotate`**:
   - `translate(x/16, y/16, z/16)`, где x, y, z — pivot в пикселях;
   - `rotationZYX(zRot, yRot, xRot)`, в радианах; матрица Rz·Ry·Rx, то есть к вершине сначала применяется X, потом Y, потом Z;
   - `scale(xScale, yScale, zScale)`, если не 1.
4. **Ванильные pivot рук** (`HumanoidModel.createMesh`):
   - right_arm: `PartPose.offset(-5, 2, 0)`, куб `addBox(-3, -2, -2, 4, 12, 4)`;
   - left_arm: offset `(5, 2, 0)`, куб `addBox(-1, -2, -2, 4, 12, 4)`, mirror.

   У `PlayerModel` со slim-руками x руки временно сдвигается на ±0.5 px (1.20.1).
5. **`ItemInHandLayer.renderArmWithItem` / `submitArmWithItem`**:
   - `rotX(-90°)`;
   - `rotY(180°)`;
   - `translate(±1/16, 2/16, -10/16)`: знак «+» для правой руки, «−» для левой.

   В 26.2 у детёнышей вместо этого `(0, 1, -4.5)/16`. Там же добавлены анимация укола копьём (`SpearAnimations`) и `animateUseItem`.
6. **`ItemTransform.apply(leftHand, pose)`** (контекст `THIRD_PERSON_RIGHT_HAND` / `_LEFT_HAND`):
   - `translate(t)`. При загрузке JSON значение умножается на 1/16 и ограничивается ±5 блоками (то есть ±80 px). Для левой руки x инвертируется.
   - `rotationXYZ(rx, ry, rz)`, матрица Rx·Ry·Rz, к вершине применяется сначала Z, потом Y, потом X. Для левой руки ry и rz инвертируются.
   - `scale(s)`, ограничение ±4.
   - `translate(-0.5, -0.5, -0.5)`: центрирование модели предмета 0..16 px. В 26.2 этот сдвиг внутри `apply`; в 1.20.1 его делал `ItemRenderer` [исх. 26.2; про 1.20.1 не проверено построчно].
7. **Вершины модели предмета**: элементы JSON в координатах 0..16 px, делённые на 16.

Источники:
- [Model, раздел display](https://minecraft.wiki/w/Model): контексты отображения, лимиты (−80…80 и 4), «translation применяется до rotation»;
- код по ссылкам выше: `ItemInHandLayer.java`, `HumanoidModel.java`, `ModelPart.java`, `ItemTransform.java`, `LivingEntityRenderer.java`.

### 3.2. Где именно оказывается «точка хвата»

Мой вывод из шагов 4–5; проверить тестом.
- В локальных координатах правой руки (px, Y вниз вдоль руки) начало системы предмета: `Rx(-90)·Ry(180)·(1, 2, -10) = (-1, 10, -2)`.
- Это **центр руки по X** (куб −3…1, центр −1), **низ кисти** (y = 10) и **передняя грань** (z = −2). Для левой руки точка зеркальна: `(1, 10, -2)`.
- Оси сокета в координатах руки:
  - +X сокета = −X руки;
  - +Y сокета = −Z руки (вперёд, если рука опущена);
  - +Z сокета = −Y руки (к плечу).
- Поверх этого применяется `display.thirdperson_*` модели предмета.
- Вывод для своих мобов: если у моба своя модель руки, но предмет рисует ванильный `ItemInHandLayer`, хват окажется в точке **pivot + (−1, 10, −2) px**, в повёрнутой системе руки. Длина руки 12 px от pivot на −2 и торец на +10 тут жёстко заложены. Если наша рука длиннее или короче, нужно либо переопределить `translateToHand` и добавить сдвиг, либо рисовать предмет своим слоем от кости-сокета.

### 3.3. GeckoLib

[Исходники](https://github.com/bernie-g/geckolib), ветка main, GeckoLib 5:
- `ItemInHandGeoLayer` ожидает кости **`RightHandItem`** и **`LeftHandItem`** (имена можно передать свои). Для `THIRD_PERSON_*_HAND` он делает `rotate(X, -90°)` и `translate(0, 0.125, -0.0625)`. Для щита добавляется ещё сдвиг `(0, 0.125, ∓0.25)`, для левого щита поворот Y на 180°. Дальше вызывается базовый рендер стака на кость.
- `BlockAndItemGeoLayer` служит базой для «предмет или блок на кости». Для блоков он делает `translate(-0.25)` и `scale(0.5)`.
- **Практический вывод**: в GeckoLib-моделях хват задаётся **отдельной костью-сокетом** с pivot там, где нужен хват. Это ровно наш «hand socket».
- В GeckoLib 5 методы переименованы: `renderStackForBone` стал `submitItemStackRender` ([changelog 5.x](https://modrinth.com/mod/geckolib/version/5.0)). При чтении старых туториалов нужно делать поправку на это.

### 3.4. Bedrock

[Схема geometry 1.21.0](https://learn.microsoft.com/en-us/minecraft/creator/reference/content/schemasreference/schemas/minecraftschema_geometry_1.21.0):
- **locators** на кости: точка (`offset`, `rotation`, `ignore_inherited_scale`), которая следует за костью в анимации.
- **binding** (Molang): к какой кости родителя крепится корень attachable.
- У геометрии есть свои `item_display_transforms` с `rotation_pivot` и `scale_pivot`, лимиты: translation ±80, scale 0…4.

[Attachables](https://wiki.bedrock.dev/items/attachables):
- `q.item_slot_to_bone_name(context.item_slot)` отдаёт `rightitem` для main_hand и `leftitem` для off_hand;
- в геометрии игрока есть кость `rightItem`;
- вики отмечает необъяснённый сдвиг привязанных костей на −24 по Y (те же 24 px, что origin Java-модели).

Конвенции знаков Bedrock и Java различаются: по опыту Blockbench при конвертации инвертируются X-координата и повороты X/Y [не проверено].

### 3.5. Чек-лист: поза в Blender совпадает с игрой

1. **Единицы.** 1 блок = 16 px. Рекомендую в Blender **1 BU = 1 блок**, Grid → Scale 1/16 = 0.0625, снап Increment с Absolute Grid Snap. Тогда все pivot и размеры кратны 1 px. Полупиксели (0.5 px) допускать только сознательно.
2. **Оси.**
   - Персонаж в Blender смотрит в −Y (вид спереди, Numpad 1), Z вверх, ноги на Z = 0.
   - Перевод точки Blender (Bx, By, Bz) в блоках в пространство модели Java в px: **`mx = 16·Bx`, `my = 24 − 16·Bz`, `mz = 16·By`**. Это собственное вращение (det = +1), зеркала нет. Мой вывод из §3.1, проверить тест-моделью.
3. **Повороты.**
   - `xRot` модели соответствует повороту вокруг Blender X;
   - `yRot` соответствует **−** повороту вокруг Blender Z;
   - `zRot` соответствует повороту вокруг Blender Y.
   - Порядок Java «сначала X, потом Y, потом Z» соответствует Blender Euler-режиму **XZY** (X применяется первым) [вывод, проверить].
   - В three.js кость Java-модели: `rotation.order = 'ZYX'` (матрица Rz·Ry·Rx), `ItemTransform`: `'XYZ'`.
4. **Pivot = origin кости.** Голова кости в Blender (или origin объекта у кубоидной сборки) должна совпадать с `PartPose.offset`. Куб хранится относительно pivot (`addBox(x0, y0, z0, w, h, d)` в px).
5. **Зеркалирование лево и право.** В Java левая рука — отдельный ModelPart с `mirror()` UV, а не отрицательный scale. В Blender симметричные части дублировать с Symmetrize или −X **с применённым масштабом** (Apply Scale), иначе получится отрицательный детерминант. Для предмета в левой руке игра сама инвертирует tx, ry и rz (§3.1 п. 6).
6. **Сокет руки в Blender.** Пустышка `Socket_R` с родителем кость руки. Её локальная позиция в px относительно pivot руки: (−1, 10, −2), в Blender-осях после перевода из п. 2. Ориентация сокета: `Rx(-90)·Ry(180)` в системе модели. Поверх неё дочерняя пустышка `Item_R` с трансформом `display.thirdperson_righthand` выбранного предмета и сдвигом (−8, −8, −8) px. Модель предмета (`handheld`-спрайт, экструдированный на 1 px) крепится к `Item_R`. Для левой руки то же самое: (1, 10, −2), с инверсией tx, ry, rz.
7. **Тест-сцена.** Скелет ванильного зомби (из таблицы §3.1) с железным мечом в правой руке. Скриншот в игре и рендер Blender/three.js с одной камеры (ортографической спереди и сбоку) должны совпасть с точностью до пикселя. Если меч «в груди», чаще всего перепутан знак my или не применён `scale(-1,-1,1)`.
8. **Анимация.** Кость-сокет анимируется только через родителя (руку), иначе хват уедет в игре, где сокет вычисляется формулой. Для GeckoLib сокет сам является костью `RightHandItem`, его можно анимировать свободно.
9. **Масштаб моба.** Если моб масштабирован (`scale` в рендерере), он применяется до `translate(0,-1.501,0)`, то есть origin 24 px тоже масштабируется. В Blender масштабировать корень, а не меши.

## 4. Броня на своих моделях

- **Ванильный армор-меш** [исх. 1.20.1 и 26.2, `LayerDefinitions`]:
  - `OUTER_ARMOR_DEFORMATION = CubeDeformation(1.0)`: шлем, нагрудник, ботинки;
  - `INNER_ARMOR_DEFORMATION = CubeDeformation(0.5)`: поножи;
  - текстура **64×32**;
  - пиглины: outer 1.02;
  - в 26.x у детёнышей отдельные анизотропные раздувы, например `(-0.1, 0.5, 0.3)`.
  - Геометрия та же, что у `HumanoidModel` (голова 8×8×8, тело 8×12×4, руки и ноги 4×12×4), только раздута. Шлем рисуется на голове, оверлей шляпы раздут ещё на 0.5.
- **Equipment assets** [вики, [Equipment](https://minecraft.wiki/w/Equipment)]:
  - с 1.21.2 (24w36a) лежат в `assets/<ns>/models/equipment/`, с 1.21.4 (24w45a) в `assets/<ns>/equipment/<name>.json`;
  - формат: `{"layers": {"humanoid": [{"texture": "ns:name"}], "humanoid_leggings": [...]}}`;
  - текстура ищется в `textures/entity/equipment/<layer_type>/<path>.png`;
  - типы слоёв: `humanoid` (голова, грудь, ноги-ботинки), `humanoid_leggings`, `humanoid_baby` (26.1), `wings`, `wolf_body`, `horse_body`, `llama_body`, `happy_ghast_body`, `nautilus_body` и сёдла;
  - у слоя есть опциональные `dyeable.color_when_undyed`, `use_player_texture` (только wings), `trim_overrides`.
- **Броня на нестандартных мобах:**
  - (а) **Ванильный путь.** Свой армор-меш (как `PiglinModel.createArmorMeshSet`) с той же UV-раскладкой 64×32, но со своими pivot и размерами. Тогда любой ванильный и наш equipment-ассет ляжет на моба.
  - (б) **GeckoLib** `ItemArmorGeoLayer`: рендерит ванильную и GeckoLib-броню **по костям**. В `RenderData` указываются кость и сегмент (head / chest / left_arm / right_arm / left_leg / right_leg / left_foot / right_foot). Для GeckoLib-брони кости называются `armorHead`, `armorBody`, `armorRightArm`, `armorLeftArm`, `armorRightLeg`, `armorLeftLeg`, `armorRightBoot`, `armorLeftBoot` [исх. `GeoArmorRenderer`]. Шаблон Armor в Blockbench-плагине GeckoLib ставит эти кости правильно ([wiki GL4](https://github.com/bernie-g/geckolib/wiki/Geckolib-Armor-(Geckolib4))).
- **Уникальная броня моба, которая падает как декор:**
  - Модель брони делать **на гуманоидной раскладке** (pivot как у `HumanoidModel`). Тогда предмет-трофей сядет на игрока, стойку и манекен без своего рендерера: достаточно equipment-ассета.
  - Объёмные детали (наплечники, гребни) выходят за пределы стандартного меша, для них нужен свой армор-рендер. В NeoForge есть хук для кастомной модели брони, в GeckoLib есть `GeoArmorRenderer` [не проверено для актуальной версии NeoForge].
  - На своём мобе та же броня надевается либо через вариант (а) с подогнанными pivot, либо через запечённую в модель моба геометрию с тем же UV.
- **Стойка и манекен:**
  - Armor stand использует свои `ArmorStandArmorModel` с теми же раздувами 0.5 / 1.0 [исх. 1.20.1].
  - **Mannequin** (`minecraft:mannequin`, Java 1.21.9, 2025) — `class Mannequin extends Avatar` [исх. 26.2]. Рисуется моделью игрока (skin через `profile`, модель wide или slim), имеет позы `STANDING`, `CROUCHING`, `SWIMMING`, `FALL_FLYING`, `SLEEPING`, поля `immovable`, `hide_description` и экипировку. Без profile он в скине Alex (slim), по [Kore docs](https://kore.ayfri.com/docs/helpers/mannequins) [вики/вторичка]. Для нас это значит, что декоративная броня должна выглядеть корректно и на **slim-руках** (3 px) тоже.

## 5. Blender-пайплайн для кубоидных моделей

- **Дисциплина.**
  - Только кубоиды (6 граней, прямые углы), повороты кубов по возможности кратны 22.5°. Ванильные JSON-модели предметов и блоков исторически ограничивают поворот элемента одной осью и шагом 22.5° (в новых версиях ограничение могли ослабить [не проверено]); у entity ModelPart ограничений нет.
  - Плоскости нулевой толщины допустимы (жабры axolotl).
  - Без bevel, subdivision и smooth shading: Auto Smooth выкл., все грани Flat.
- **UV и плотность.**
  - 1 px геометрии = 1 тексель. Удобна box-UV-раскладка в стиле Minecraft (развёртка «крестом», как `texOffs`).
  - Контроль плотности: [Texel Density Checker](https://github.com/mrven/Blender-Texel-Density-Checker) (mrven), цель 16 px/блок при 1 BU = 1 блок.
  - Текстура: Image Texture → Interpolation **Closest**, без мипмапов в превью.
- **Инструменты.**
  - [MCprep](https://github.com/Moo-Ack-Productions/MCprep) (Moo-Ack! Productions, с 2013): подготовка Minecraft-материалов (Closest), спаунер ригов мобов, импорт миров. Полезен как источник ванильных ригов для сравнения пропорций.
  - [Mcblend](https://github.com/Nusiq/mcblend) (Nusiq, MIT; README: Blender 5.2): экспорт и импорт моделей **и анимаций Bedrock** (`.geo.json` и `.animation.json`), генерация UV и шаблонных текстур. Bedrock-формат и есть формат GeckoLib, так что это кандидат на основной экспортёр из Blender для GeckoLib-пути [совместимость с GeckoLib 5 не проверена].
  - [Blockbench](https://github.com/JannisX11/blockbench) (JannisX11, с 2017): экспорт glTF (с анимациями), импорт в Blender встроенным glTF-импортёром. Пригоден для взятия референсов из открытых модов (модели Bedrock / GeckoLib открываются в Blockbench). Вкладка Display в Blockbench с манекеном игрока позволяет проверить `display`-трансформы предмета.
  - [Animated Java](https://github.com/Animated-Java/animated-java): плагин Blockbench для анимаций через display-сущности. Это альтернативный путь, если Horizon поддерживает только датапак-уровень [не проверено применимость к Horizon].
  - Шаблон Better Combat `animation_template.blend` подтверждает, что Blender-риг гуманоида пригоден для боевых анимаций в Minecraft.
- **Экспорт для three.js.**
  - Blender glTF-экспортёр [исх. `glTF-Blender-IO/.../exp/sampler.py`]: при Interpolation = `Closest` пишет `magFilter = NEAREST` (9728) и `minFilter = NEAREST_MIPMAP_NEAREST`.
  - В three.js после загрузки: `tex.magFilter = THREE.NearestFilter; tex.minFilter = THREE.NearestFilter; tex.generateMipmaps = false; tex.colorSpace = THREE.SRGBColorSpace`. Иначе на дальних планах появится мыло от мипмапов.
  - Экспорт с «+Y Up» (по умолчанию). Blender-персонаж, смотрящий в −Y, в glTF смотрит в +Z.
  - Анимации экспортировать по костям (armature) или по объектам-кубоидам с NLA-треками на каждую атаку. Частоту ключей держать кратной 20 fps (1 тик = 1 кадр), чтобы тайминги из §2 переносились один в один.
- **Предупреждение для three.js-превью.** Если воспроизводить в превью ванильную цепочку `scale(-1,-1,1)`, получится отрицательный детерминант: three.js сам перевернёт порядок обхода граней, но нормали и освещение нужно проверить. Проще держать превью в Blender-осях и пересчитывать в Java-оси только при экспорте (формулы из §3.5 п. 2–3).
