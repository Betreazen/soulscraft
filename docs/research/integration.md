# SoulsCraft: совмещение с Path-of-craft-tree и RustCraft

Дата: 2026-11-11. Статус: исследование перед интервью. Ничего не собиралось и не запускалось. Исходное видение: [../design/00-vision-raw.md](../design/00-vision-raw.md). Ответы автора на вопросы раздела 6 — в [../design/01-decisions.md](../design/01-decisions.md), раунд 1.

Источники:

- Path-of-craft-tree (дальше PCT): репозиторий `C:\Claude code projects\path-of-craft-tree`, в сборке сервера тег `v0.3.0`. Главный документ: `docs/design.md`.
- RustCraft: `C:\Claude code projects\rustcraft`, спецификация `docs/design/02-spec.md`, контракт с PCT `docs/design/path-of-craft-tree-contract.md`, исследование движка `docs/research/horizon-modding-capabilities.md`.
- Движок: исходники Horizon на коммите `7e4e421`, справочник `docs/native-mods.md` (дальше `NM`).

Пометки, как в исследовании RustCraft: **[И]** проверено в исходниках, **[Д]** сказано в документации движка, **[П]** вывод автора документа без проверки.

## Коротко

1. Движок подходит. Свои цели ИИ на Rust, навигация, атака, эффекты, броня и оружие мобов, хуки урона, отбрасывания и спавна уже есть. Новый вид моба делается только по шаблону `minecraft:zombie`, `villager` или `wandering_trader`, а модель и анимации мод рисует сам.
2. Главная связь с PCT: прогресс игрока. PCT сейчас никому не отдаёт уровни игрока. Нужен небольшой контракт, предложение в разделе 3.1.
3. Опыт Воина и Стрелка PCT считает по таблице `mob_health` в `data/tree.json` по виду моба, а не по настоящему здоровью. Новых мобов нужно вписать в эту таблицу. Усиленный зомби даст столько же опыта, сколько обычный, если ничего не менять.
4. Маяк спавна RustCraft отдал этому моду (решение раунда 10, P4 спецификации). Спавном и силой врагов управляет только мод с врагами, спорить модам не о чем.
5. Мод не должен трогать служебных мобов RustCraft: невидимое сиденье гарпуна и зиплайна сделано мобом (способ b2).
6. Все три мода собираются в один движок на одном коммите Horizon. Мод с врагами, скорее всего, придётся сделать trait-модом из-за хука спавна, и тогда нужна регрессионная проверка PCT.

Риски движка:

- **Свои модели.** Модели и текстуры живут в контент-моде, а не в бандле, как у RustCraft. Анимацию конечностей мод считает сам: слои крепятся к системе координат моба, а не к костям.
- **Trait-мод.** Без него молчит хук спавна. Если мод с врагами станет trait-модом, в общей сборке заговорят хуки, которые у PCT молчали (таблица «Ловушка `mods().is_empty()`» в исследовании RustCraft). PCT обходит их инъекцией HEAD в настоящую функцию, но поведение нужно перепроверить.
- **Нагрузка.** Умные цели думают каждый тик. Решения «отойти», «найти укрытие», «занять высоту» надо считать редко, раз в 10–20 тиков, и ограничить число умных мобов вокруг игрока.
- **Сохранение состояния цели.** Поля цели живут, пока жив моб в памяти. Что должно пережить выгрузку чанка (уровень моба, его ступень снаряжения), хранится во вложении `Holder::Entity(mob.id)` [Д] `NM:3646-3650`.

## 3. Предложения по совмещению с PCT

### 3.1. Как мод узнаёт прогресс игрока

PCT хранит профиль в своих файлах мира и наружу уровни не отдаёт. Канал `pct-machine` односторонний: другой мод может только сообщить о событии, ответа нет.

Варианты:

| Вариант | Как | Плюсы | Минусы |
| --- | --- | --- | --- |
| А. PCT пишет сводку в данные игрока | PCT кладёт в `native_player_persistent_data(uuid)` короткий раздел, например `pct: { total, melee, archery, defense }`. Мод с врагами только читает | Нет зависимости при сборке, как у `pct-machine`. Без PCT раздела нет, мод работает по снаряжению | Небольшая правка в PCT и новая версия тега |
| Б. Мод считает силу сам | По броне и оружию игрока: `native_attribute(uuid, "minecraft:armor")`, урон оружия в руке | PCT не трогаем | Не видит узлы дерева: игрок с 300 очками в голой броне считается новичком |
| В. Оба | Сила = уровни из PCT и снаряжение | Ближе всего к цели баланса из записи | Две формулы для настройки |

Рекомендация: **В**, со сводкой по варианту А. Данные игрока проверены документацией [Д] `NM:2924-2927`, в игре не проверялись.

**Согласовано с PCT (раунд 8, 2026-11-12).** Ключ `pct:summary` в данных игрока, значение — строка JSON (`Tag::String`, ключи по алфавиту); если хранилище примет только составной тег, те же поля вложенным тегом. SoulsCraft читает оба вида (`mod/soulscraft/rules/src/pct.rs`).

```json
{"v":1,"levels":{"archery":[L,75],"defense":[L,75],"melee":[L,75]},"ranks":{"archery":[R,Rmax],"defense":[R,Rmax],"melee":[R,Rmax]}}
```

- `levels` — уровень ветки и максимум (`max_level` из `tree.json`, сейчас 75); растёт с опытом.
- `ranks` — рабочие ранги узлов ветки (с общими очками, вложенными в неё; выключенные большие узлы не считаются) и все ранги ветки.
- PCT только добавляет поля; `v` растёт лишь при несовместимой правке. Читатель пропускает незнакомые поля и не принимает другую `v` (тогда сила по снаряжению).
- PCT пишет сводку при входе, повышении уровня боевой ветки, изучении, выключении и включении узла, сбросе дерева; без игрока остаётся последняя. Только свой ключ, остальные ключи общего составного тега сохраняются. Отладка: консольная `pct_selftest summary`. Выходит в PCT v0.4.4.

**[И] Канал есть на 7e4e421.** `native_player_persistent_data(uuid) -> Option<Tag>` и `native_set_player_persistent_data(uuid, Tag)` работают с одним составным тегом `NeoForgeData` на игрока, общим для всех модов (`game/native_player_state.rs:381-408`): бандл SoulsCraft читает ключ PCT без зависимости от PCT. Ловушка: `native_place` — внутри действия игрока (`lan_acting`) достижим только он сам, для других чтение даёт None (там же, 386-391). Поэтому SoulsCraft читает сводки на своём тике уровня раз в 20 тиков (и сразу для нового игрока) в кэш, None не стирает известное, а P считается из кэша (`mod/soulscraft/power.rs`; тест `an_unreachable_read_keeps_the_cached_summary`).

### 3.2. Опыт за новых и усиленных мобов

Сейчас опыт за убийство — число из таблицы `mob_health` по виду моба. Отсюда три следствия:

1. Каждый новый вид мода нужно вписать в `mob_health` (а боссов — в `bosses`) в `data/tree.json` PCT. Иначе берётся значение по умолчанию.
2. Усиленный обычный зомби даёт опыт обычного зомби.
3. Если опыт будет расти вместе с силой моба, а сила моба растёт с уровнем игрока, получится разгон: сильнее игрок, сильнее мобы, больше опыта, быстрее уровни. Таблица по виду этот разгон гасит.

Решить на интервью: оставить опыт по виду или давать надбавку за усиление (например, отчёт `pct-machine`-подобной командой или множитель в той же сводке).

**Договорённость с PCT (2026-11-13, PCT v0.4.6).** Надбавка решена (раунд 1, гипотеза Г3), канал — вариант А, метка сущности:

- SoulsCraft ставит усиленному мобу ровно одну метку `pct.xpNNN`, где NNN = round(100·(1 + 0,5·(множитель здоровья − 1))), целое от 1 до 500; при смене силы старая метка снимается.
- PCT читает метки через `native_entity_tags` (API 386) во всех местах, где платит за убийство: удар игрока (`mob_killed`), стрелы и трезубец, отчёты машин RustCraft (турели, забойщик). Метка видна, пока сущность не удалена, в том числе во время анимации смерти. Несколько меток — берётся наибольшая; без метки ×1. Урезание за мобов из спавнера перемножается с надбавкой.
- Ограничение: для отчётов машин моб ищется в текущем уровне; моб в другом измерении даёт ×1.

### 3.3. Порядок хуков урона

Оба мода слушают урон. Предложение: мод с врагами меняет урон моба раньше (выше приоритет), узлы PCT снижают уже итоговый урон. Тогда Каменная кожа, Шипы и Щит-стена работают от настоящего удара.

### 4.1. Модули турелей (RustCraft, раунд 30, спецификация §27, 2026-11-12)

Решение автора в RustCraft: турели связываются с волнами алтаря, как в жанре защиты точки.

- **Модули эффектов:** кровотечение, яд, замедление. На одном выстреле складываются; одинаковые складываются в стопку, замедление — не больше 60%.
- **Модули поддержки:** лечение, защита, сила, скорость. Турель переходит в режим поддержки: усиливает игроков в 6 блоках и не стреляет по мобам. Усиления слабее первого черновика RustCraft.
- **Сопротивление по типу моба.** Нежить не травится, как в ванили. Элитные мобы и боссы SoulsCraft получают эффекты турели на половину длительности.
- Все числа — гипотезы.

Договорённость SoulsCraft и RustCraft (контракт RustCraft §27.1):

| Вопрос | Ответ SoulsCraft |
| --- | --- |
| Чьё кровотечение | Одно на все моды, ведёт SoulsCraft: `soulscraft:bleeding`, числа в `data/mobs.json`, раздел `effects`. RustCraft (и PCT) накладывают его по id, если SoulsCraft в сборке, иначе считают урон сами. Может ли мод Horizon зарегистрировать свой эффект с иконкой и тиком урона — проверяет прототип; если нет, общий остаётся только набор чисел и правил, а таймер урона ведёт каждый мод сам |
| Сопротивления | Поле `turret_effects` у моба в `data/mobs.json`: множитель длительности эффекта турели, `0` — иммунитет, нет ключа — 1. Пример латника: `{"poison": 0}`; громилы (элитный): `{"bleed": 0.5, "poison": 0.5, "slow": 0.5}`. Для ванильных мобов RustCraft берёт нежить по ванильному тегу. Файл лежит в контент-моде SoulsCraft, путь сообщит SoulsCraft вместе с первым бандлом |
| Прятаться от турелей | Как в раунде 1: умные мобы прячутся от стреляющих турелей. Турель поддержки не стреляет — от неё не прячутся |
| Как отличить турель (2026-11-13) | Блок один — `rustcraft:turret`. С 8-го среза RustCraft турель пишет в данные block entity поле `role`: `"attack"` или `"support"`. Мобы прячутся только от `attack`. Турель без энергии не стреляет, но роль у неё прежняя |
| Что громила не ломает (2026-11-13) | Всё пространство имён `rustcraft:` — часть блоков RustCraft (рельсы монорельса) не имеет block entity, поэтому правила «не ломать block entity» мало |
| Совместная проверка | RustCraft добавит консольную команду `rustcraft_testkit turret <x> <y> <z> [modules=…] [owner=…]`: заряженная турель с модулями одной строкой. Самотест SoulsCraft ставит турели у алтаря и проверяет иммунитет латника к яду, половину длительности у громилы, `soulscraft:bleeding` от модуля и засчитывание убийства владельцу |

Сейчас в сборке сервера (`minecraft-pack/pack.json`) только PCT `v0.3.0` на `nightly-2026-11-08-fdc87ae`. Мод с врагами придёт в пакет так же, через тег своего репозитория.

### 4.2. Убийства машин RustCraft в книге охотника (договорено 2026-11-14)

Раунд 14 (1): убийство стражем RustCraft засчитывается в книге так же, как убийство турелью. Договорились с сессией RustCraft о своём отчёте, который не зависит от PCT.

| Что | Как |
| --- | --- |
| Команда | SoulsCraft регистрирует консольную команду `soulscraft-kill <source> <owner> <entity> <type> <x> <y> <z>` (уровень 4). `source` — `turret` или `guard`; `owner` — UUID владельца, 32 шестнадцатеричных знака без дефисов; `entity` — id убитого моба; `type` — его тип (`minecraft:zombie`, `soulscraft:revenant`); `x y z` — целые координаты блока, где моб умер |
| Сторона RustCraft | Каждый тик проверяет `native_command_info("soulscraft-kill")`. Если команда есть, на каждое убийство машиной запускает её через `native_run_mod_command` рядом со своим отчётом PCT. Турель — с RustCraft 0.10.0 (срез 10). Страж (рабочий с инструментом-стрелком) шлёт ту же строку с `guard` с RustCraft 0.11.0 (2026-11-15) |
| Засчитывание | Владелец получает убийство, если стоит в 32 блоках от места смерти (`credit.radius_blocks` в `data/book.json`); `guard` считается ровно как `turret`. Место смерти берётся из услышанной смерти моба, а если её не было за 100 тиков — из `x y z` отчёта |
| Старый отчёт | Пока на стенде нет RustCraft 0.10.0, читается и `pct-machine kill <owner> <entity> <type>` — тот же разбор (`soulscraft_rules::book::machine_kill`). Если для одной смерти пришли оба отчёта, убийство засчитывается один раз |
| Проверки | Тесты крейта разбирают обе строки; самотест `book_kill_command` запускает `soulscraft-kill` на консоли и проверяет, что турель и страж засчитаны владельцу рядом, а не дальнему, и что два отчёта одной смерти дают одно убийство. Когда RustCraft 0.10.0 будет на стенде — сценарий с `rustcraft_testkit turret` в группе `turret` |

### 4.3. LetsCam читает фазы атак (договорено 2026-11-15)

- LetsCam (клиентский мод записи) читает из реплея наши сообщения канала `soulscraft:state` (формат — `rules/src/wire.rs`, версия 1) и подписывает кадры листов фазой атаки: с `/sc debug on` — нашей меткой (`revenant slash windup 7`), без неё — клипом и тиками от старта (`overhead +12`). ## 5. Рост врагов при нескольких игроках

Сила моба считается в момент спавна и дальше не меняется [П]. Варианты для группы игроков рядом:

| Вариант | Как | Что плохо |
| --- | --- | --- |
| Ближайший игрок | Сила по игроку, ближайшему к точке спавна | Новичок рядом с ветераном получает мобов ветерана, если стоит ближе |
| Сильнейший в радиусе | Максимум по игрокам в 64 блоках | Новичку в группе тяжело |
| Среднее в радиусе | Среднее по игрокам в 64 блоках | Ветерану скучно |

Рекомендация на обсуждение: ближайший игрок, а число игроков рядом слегка повышает долю умных мобов. Так каждый чаще дерётся с мобами своего уровня.

## 6. Что решить на интервью

1. Новые виды мобов (своя модель и мувсет) или новые поведения для ванильных мобов, или оба. Сколько видов в первом срезе.
2. Что входит в прогресс игрока: уровни PCT, снаряжение, время в мире. Делаем ли сводку PCT по 3.1.
3. Опыт за усиленных мобов: по виду или с надбавкой (3.2).
4. Формула роста: насколько здоровье, броня, урон, скорость растут от новичка до эндгейма. Цель из записи: эндгейм-игрок ощутимо сильнее, но не сокрушительно.
5. Лестница снаряжения: пороги прогресса для каждой ступени, доля неполных комплектов и щитов.
6. Маяк: что он делает, ступени, нужна ли энергия RustCraft.
7. Прячутся ли мобы от турелей и атакуют ли машины.
8. Усиливаются ли мобы из спавнеров.
9. Как считать силу моба при нескольких игроках (раздел 5).
10. Насколько больше врагов спавнится и в каких измерениях.
11. Порядок работ: как у RustCraft (спецификация, витрина, арт, затем код) или сразу вертикальный срез.

## 7. Что проверить прототипом первым

1. Своя цель на ванильном зомби: отход после серии ударов и ожидание опущенного щита.
2. Свой вид моба по шаблону `minecraft:zombie` с моделью через `native_mob_submit` и читаемым замахом, на выделенном сервере с двумя клиентами.
3. Изменение здоровья, брони и скорости моба из своего хука; что из этого переживает выгрузку чанка.
4. Trait-мод с `native_potential_spawns` в одной сборке с PCT: что изменилось в поведении PCT.
5. Стоимость: 50 умных мобов вокруг игрока, замер через `native_mob_cost_sampling`.

## 8. Что показал первый код (2026-11-12)

Итоги прототипов — [../../prototypes/README.md](../../prototypes/README.md). Здесь — факты о движке и совмещении, найденные по пути. Пометки те же: **[И]** проверено в исходниках или в игре на стенде, **[П]** вывод.

- **[И] Trait-мод пока не нужен.** Все хуки, на которых стоит первая итерация, вызываются без проверки `mods().is_empty()`: `level_tick_post`, `register_commands`, `perform_command`, `perform_console_command`, `living_incoming_damage` v1, `net_from_server`, `mob_submit`, тики эффекта мода. Цели моба ставятся инъекцией в саму функцию `native_register_goals` (`mobs/ai.rs:464`): её диспетчер доходит только до trait-модов (`native_client_hooks.rs:123-127`). Места вызова — шапка `mod/soulscraft/horizon-mixin.toml`. Trait-мод понадобится для естественного спавна (`native_potential_spawns`), это П4.
- **[И] Живой тип на шаблоне зомби работает в игре** (docs/mods.md говорил «не пробовали»): спавн командой и `native_summon`, свои атрибуты из `entity_type`, метки, сохранение с чанком.
- **[И] Атакующий в хуке урона.** v3 с атакующим ждёт trait-мод (`native_hooks.rs:9676-9680`); v1 даёт `causing`, который бывает 0. Щит латника берёт атакующего из `causing`, иначе ближайшего игрока.
- **[И] `/attribute` на броню типа мода падает** (`game/commands/world_cmds.rs:1376-1381`): мод ставит броню в карту атрибутов моба сам.
- **[И] Неуязвимость после удара съедает быстрый второй удар** (двойной взмах ловчего): мод обнуляет кулдаун цели перед поздним ударом многоударной атаки.
- **[И] Общее кровотечение `soulscraft:bleeding` возможно.** Эффект объявляется контент-модом (`data/<id>/horizon/mob_effect/`, docs/mods.md:316-328), а его урон даёт бандл через хуки `should_apply_effect_tick_this_tick` и `apply_effect_tick` (`game/potions.rs:1128-1142`). В `apply_effect_tick` игра только для чтения: удар ставится в очередь и наносится в следующем тике уровня. Числа — `data/mobs.json`, `effects.bleeding` (гипотеза). Значка эффекта пока нет: без `textures/mob_effect/bleeding.png` движок рисует «нет текстуры».
- **[И] Сводка PCT согласована** (раунд 8, формат и канал — 3.1): ключ `pct:summary` в PCT v0.4.4. До неё P считается по броне и оружию (Г1 при `T = 0`) или задаётся `/sc p`; `/sc pct <игрок> <ближний> <стрельба> <защита>` пишет игроку-боту такую же сводку для проверки, `/sc power` показывает P каждого игрока по частям.
- **[И] Числа для других модов.** Турели RustCraft читают `turret_effects` и `effects.bleeding` из копии `data/mobs.json` в контент-моде: `horizon-mods/soulscraft/data/soulscraft/mobs.json` от папки сервера или instance.

## 9. Что показала вторая итерация: алтарь и ивент (2026-11-13)

Итоги — [../../prototypes/p6-altar.md](../../prototypes/p6-altar.md). Пометки: **[И]** проверено в исходниках `7e4e421` или в игре на стенде, **[П]** вывод.

- **[И] Изменения блоков без сканирования.** Хук `block_changed` (`GameLevel::native_block_changed`, вызов `observe_block_changed`, `game.rs:1388-1392`) слышит каждый `Level.setBlock` авторитетного сервера со старым и новым состоянием, без проверки `mods()`. Уровень в нём только для чтения, и хук зовётся внутри любого `setBlock`, в том числе наших `setblock` из тика уровня: мод держит в нём только замок своей очереди и разбирает очередь в тике. Имя блока — таблица фактов уровня (`facts.get(id).name`), свойства — реестр в тике (`pack.assets.registry.state(id)`).
- **[И] Ядро находится само.** У блока мода без шаблона с block entity block entity даёт хук `block_entity` (API 15, с API 129 на любом шаблоне), тикает ли он — `block_entity_ticks`; тик (`tick_mod_block_entity`, `native_hooks.rs:12073-12096`) сообщает позицию, так ядро в загруженном чанке находится без сканирования чанков.
- **[И] Свет блока по состоянию не меняется.** `light` в объявлении блока один на все состояния (trophy-effects.md, 5): горящая жаровня (`lit`) светится только моделью, свет мира у неё один. Чтобы светила только горящая, нужен шаблон со свойством `lit` и своим поведением (печь, свеча) — ни один не подходит без чужого поведения [П].
- **[И] Меню без меню-типа.** Экран мода открывается на клиенте (`native_mod_screen_open`) из тика окна по сообщению сервера; кнопки идут серверу модовыми сообщениями (`net_from_client`). Слоты и меню-тип не нужны.
- **[И] Боссбар и предупреждение — команды.** Хелперы `native_boss_bar` и `native_title` в `7e4e421` — ожидающий API (`@API:boss_bar@`, `@API:title@`), поэтому бар и титры идут консольными командами `bossbar` и `title` (`native_run_command`), звук — `playsound`.
- **[И] Ванильный зомби под управлением мода.** Цели и цели-мишени моба открыты (`Mob.ai.goals`, `ai.targets`, `mobs/ai.rs:50-62`): сервер ивента очищает их у зомби волны при первой встрече и ведёт его сам (`native_mob_navigate`, удары `native_hurt_entity`), хук `register_goals` для этого не нужен. Горение днём снимается в копии типа моба.
